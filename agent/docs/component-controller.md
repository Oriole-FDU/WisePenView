# 大组件与 Controller 拆分规范

本规范用于处理同时包含多组状态、异步请求、交互流程和复杂渲染的大型组件。拆分的目标不是减少单个文件的行数，而是让状态归属、变化原因和依赖方向清晰，使一次需求变更尽量只影响一个行为域。

## 一、核心模型

将大组件视为一个组合根，而不是把全部逻辑藏进一个总 Controller。推荐结构是：

```text
顶层组件（组合与跨域编排）
├── controller A（一个内聚的行为域）
├── controller B（一个内聚的行为域）
├── controller C（第三方交互或独立子流程）
├── 纯函数 / config（无状态映射和策略）
└── parts（可独立理解的展示区域）
```

各层职责：

- 顶层组件读取 Props 和页面上下文，初始化各 Controller，显式连接它们，派生少量渲染参数，并表达最终 UI 结构。
- Controller 维护一个行为域内共同变化的状态、refs、派生数据、请求和事件，向组件暴露以用户意图命名的接口。
- 纯函数或 config 承担无状态的数据映射、列配置、规则判断和索引构建，不因使用了业务类型就包装成 Hook。
- parts 承担有独立视觉语义的 UI 区域，通过 Props 接收数据和事件，不接管不属于它的业务流程。
- service 承担领域能力和后端操作编排；Controller 只组织当前 UI 场景，不复制领域规则。

## 二、按行为域拆分

Controller 的边界由“哪些状态和行为必须共同维护一组不变量”决定，不按 JSX 区块、代码行数或 Hook 种类平均切分。一个合理的 Controller 通常能用一句稳定的业务语言说明职责，例如：

- 导航：当前节点、路径、展开状态、子节点加载和刷新。
- 交互：选中项、勾选项、排序、详情面板状态及其派生模型。
- 拖拽：传感器、拖拽会话、合法目标判断、移动请求和第三方组件适配。
- 独立子流程：回收站进入与返回、搜索会话、导入流程等具有自身状态转换的能力。
- 业务动作：创建、移动、删除、权限等命令及与这些命令绑定的弹窗状态。
- 展示策略：根据权限和上下文生成行操作、菜单项等 UI 策略。若策略无状态，优先写成纯函数；只有依赖 Hook 或场景能力时才使用 Controller。

拆分时应把一条行为链整体移动：触发事件、状态、派生值、异步请求、成功或失败处理以及 cleanup 应属于同一个所有者。不要把 state 留在组件、把 setter 传入 Controller，再从 Controller 返回同义回调；这种拆法只增加跳转。

文件大小不是边界判断。一段逻辑即使较长，只要围绕同一组不变量共同变化，仍可保留在一个 Controller；反之，短小但生命周期和变化原因独立的流程也值得拆出。

## 三、顶层组件保留编排

跨 Controller 的工作流应留在最靠近 UI 的共同父级，由顶层组件通过语义化回调显式连接。例如“操作成功后清空勾选并刷新列表”同时涉及交互域和导航域，应由组件组合这两个能力，而不是让一个 Controller import 或读取另一个 Controller。

顶层组件适合保留：

- Props、路由参数和作用域的解析。
- Controller 的初始化顺序和数据流连接。
- 同时协调多个 Controller 的短流程。
- 仅用于当前 JSX 组合的轻量派生值和事件适配。
- 页面骨架、区域组合和 Controller 输出到组件 Props 的映射。

顶层组件不应重新承载某个行为域的请求细节、状态机或长条件策略。判断标准不是组件还有多少行，而是阅读顶层代码时能否快速看出“有哪些能力、它们如何协作、界面如何组成”。

## 四、Controller 契约

### 输入

- 只接收本行为域需要的稳定数据和语义化回调，不传入整个父组件 Props 或另一个 Controller 的完整返回值。
- 跨域协作使用 `onSuccess`、`onEnterFolder` 等意图明确的回调，不直接依赖兄弟 Controller。
- 领域能力通过现有 `useXxxService()` 获取，不把 service 实例沿组件树透传。

### 输出

- 返回该行为域的最小公开能力，包括必要状态、派生结果和意图方法。
- 顶层按 `navigation.xxx`、`interaction.xxx` 等命名空间使用，避免把多个 Controller 展平成几十个同级变量后重新形成“总 Controller”。
- 优先暴露 `clearSelection()`、`enterFolder()`、`openTrash()` 等意图方法，而不是让调用方拼装多个底层 setter。底层 setter 仅在调用方确实负责该状态的直接控件绑定时暴露。
- 不暴露内部请求对象、临时 ref、缓存结构或仅供内部实现使用的中间状态。

### 依赖方向

```text
顶层组件 -> controllers -> service / 纯模型 / 第三方适配
顶层组件 -> parts
controllers -X-> 兄弟 controller
parts -X-> 页面 controller
```

Controller 之间不要互相 import、调用或共享可变对象。确需共享的无状态规则下沉到最近的纯模型模块；需要协调的运行时行为提升到顶层组件。这样可以避免循环依赖、隐藏刷新链路和隐式状态同步。

## 五、JSX 与弹窗归属

- 可独立描述、复用或单独测试的视觉区域拆成 parts。不要为了缩短文件，把每段 JSX 都变成只有一次使用的薄组件。
- 普通展示 JSX 留在组件或 parts，Controller 不应成为任意 JSX 的收纳处。
- 当一组弹窗与某个动作 Controller 的目标状态、打开关闭和成功回调强绑定时，Controller 可以返回一个语义明确的 Host 作为挂载点；Host 只负责该行为域的 overlay，不应包含页面布局。
- 静态列定义、类型到文案的映射、菜单策略等无状态内容优先放 config 或普通函数。不要仅因为它们服务于组件就命名为 Controller。

## 六、何时开始拆分

出现以下信号时，应先画出行为域再决定拆分：

- 一个组件同时管理三组以上可以独立命名的状态或流程。
- 请求、选择、拖拽、弹窗、权限策略等逻辑交错，修改一处需要理解大量无关代码。
- 单个 Hook 返回大量不同语义的字段，调用方无法看出字段属于哪项能力。
- 多个 state、ref 和 handler 总是共同修改，已形成隐含状态机。
- 第三方库适配细节淹没了页面业务语义。
- 同一概念的规则散落在渲染、事件和请求回调中。

不要设置固定行数阈值。大型表单、静态展示或顺序清晰的 JSX 可能不需要 Controller；真正的问题是变化原因混杂和状态所有权模糊。

## 七、无效拆分

避免以下做法：

- 把原组件完整搬进一个 `useXxxController`，返回几十个字段，再由组件逐项解构。它只移动了代码，没有建立边界。
- 按“请求 Hook”“所有 handlers”“所有 state”分层。一次行为变更仍要跨多个文件，内聚性反而降低。
- Controller 只接收 state 和 setter，再包装一层同义函数。状态所有权仍然不清晰。
- 为每个 JSX 片段创建单次使用组件，或为每个小事件创建 Hook。文件数增加不等于复杂度下降。
- 让 Controller 互相 import，或把一个 Controller 的完整返回对象传给另一个 Controller。依赖会重新汇聚成隐式总线。
- 为旧总 Controller 保留 wrapper、alias 或双路径。一次性迁移所有调用点并删除旧实现。
- 把领域规则、协议兼容或跨页面状态塞进页面 Controller。它们分别属于 service / mapper 或 store。

## 八、推荐拆分步骤

1. 盘点组件内的 Props、state、refs、请求、派生值、事件、服务调用、第三方适配和 JSX 区域。
2. 按共同维护的不变量和变化原因聚类，为每组写一句职责说明；无法命名的分组通常还不是稳定边界。
3. 先移出纯映射、配置和规则，减少 Controller 对无状态细节的负担。
4. 优先提取依赖单向、生命周期独立的行为域，再提取与其它能力连接较多的流程。
5. 在顶层组件显式重建跨域工作流，传递最小数据和语义化回调。
6. 删除旧总 Controller、旧 Hook、wrapper 和重复派生逻辑，全局搜索确认没有遗留调用。
7. 用行为而非文件数量验收：逐项验证加载、刷新、选择清理、异步失败、弹窗关闭、权限分支和第三方交互。

## 九、TableDrive 案例提炼

`TableDrive` 的拆分可作为边界识别案例，但不应被复制成固定目录模板：

- 原总 Controller 同时拥有导航、表格交互、拖拽、回收站和节点动作，返回值是一组展平字段，变化原因彼此混杂。
- 拆分后，导航、交互、拖拽、回收站、业务动作和行操作策略各自拥有相关状态与行为。
- 顶层组件保留“节点操作成功”“进入目录”等跨域流程，并以命名空间读取各 Controller，使能力和依赖关系在调用点可见。
- 表格行映射、索引和列配置收敛到纯 config；旧总 Controller 和旧入口同步删除，没有保留兼容层。

这个案例可复用的不是 Controller 数量，而是三条原则：状态跟随行为所有者、兄弟能力由顶层显式编排、无状态规则不伪装成 Controller。

## 十、检查清单

- [ ] 每个 Controller 都能用一句业务语言说明职责。
- [ ] 同一行为链的状态、派生值、请求和事件属于同一个所有者。
- [ ] 顶层组件能清楚展示各能力的初始化、协作和 UI 组合。
- [ ] Controller 不依赖兄弟 Controller，只通过顶层传递最小数据和语义化回调。
- [ ] 纯映射和配置没有被包装成 Hook，领域逻辑没有泄漏出 service。
- [ ] 没有仅转发 state / setter / Props 的薄 Controller 或薄组件。
- [ ] 旧总 Controller、wrapper、alias 和重复逻辑已删除。
- [ ] lint、typecheck 以及涉及的关键交互行为已验证。
