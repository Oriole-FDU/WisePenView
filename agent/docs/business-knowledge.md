# BUSINESS.md 业务知识治理

`BUSINESS.md` 用于保存不容易从代码直接推导、但会影响实现与审查的业务规则、历史决策、特殊判断与不可任意修改的约束。它不是 API 文档、一般工程规范或更改日志。

## 一、Canonical owner

- 根目录 `BUSINESS.md` 只做索引，不复制详细规则，也不记录进度或审查状态。
- `src/domains/<Domain>/BUSINESS.md` 保存跨 view、service 或 API 的 domain 规则。
- 页面或流程文档放在实际拥有该流程的模块附近，包括 `src/views/...`、`src/components/business/...` 与 `src/components/editors/<Editor>`；保存交互状态、编辑限制与用户可见流程，不按旧目录结构创建平行文档。
- 只有确实存在需要长期保存的知识才创建文档；没有内容的模块不加入根索引，也不创建空文件。
- 一条规则只能有一个主要拥有者；其他位置只链接，不重复抄写。

## 二、文档内容

模块文档按实际需要说明：范围、核心规则、状态／权限、特殊判断、禁止修改事项、历史决策和相关代码。每一条重要规则都应能回到当前代码、API 契约、PR／commit 或其他可追溯证据。文档不记录维护状态或审查日期，进度以 Git 和 PR 流程为准。

## 三、迁移与删除

1. 先盘点现有 docs、注解、测试与代码中的业务规则。
2. 确认唯一 owner 与文档粒度，再依模板创建或更新 `BUSINESS.md`。
3. 更新 README、规范、代码注解与 PR 链接，避免断链。
4. 由模块 owner 审查内容是否完整、没有重复或推测性结论。
5. 只有迁移完成且所有引用已更新后，才删除旧业务 docs；工程规范文档不得因迁移而一并删除。

## 四、审查节奏

治理按业务域批量进行，先用一至两个模块确定文档粒度与模板。一个试点 PR 可以包含多个批次，合并前必须完成两次审查：

1. 业务知识与来源审查：内容完整性、唯一 owner、代码／契约对照、迁移与引用更新。
2. 架构与行为审查：责任边界、依赖方向、公开契约与拆分前后验证。

CI 通过不能代替业务审查。迁移盘点、审查结论与覆盖进度记录在 PR，不能把一次性验收记录留在治理规范或 BUSINESS.md 中。后续批次沿用上述检查项，按业务域追加；批量之间不要求重构无关的大文件。

## 五、覆盖路线与迭代数

以目前 19 个一级业务域（不含 `_registry`、`_shared`）估算，业务知识盘点与迁移预计分 **5 轮**。每轮先确认是否存在需要长期保存的知识，没有内容的域只在 PR 记录无需创建的原因，不创建空文档或空索引：

1. **第 1 轮**：Drive、Skill domain、Skill editor workflow，确定 domain 与 editor 流程的文档粒度。
2. **第 2 轮**：Resource、Tag、Image、Document；先处理跨页面共用的资源与标签规则，再补文档与图片生命周期。
3. **第 3 轮**：Auth、User、Group、Wallet；集中确认账号、群组、权限与资产归属边界。
4. **第 4 轮**：ChatSession、ChatTurn、ChatConfig、Agent、Course、Message；整理会话、流式轮次、模型配置、代理、课程与消息状态及跨域引用。
5. **第 5 轮**：Note、Speech、ResourceInteraction、ResourceComment、ResourceFavorite、InlineComment、Admin，并做一次全局索引、重复规则与断链审查。

上述轮次只估算业务知识覆盖。大型代码文件按各批次的 ESLint 告警量逐项拆分或审查，不承诺五轮清零全仓告警。第 5 轮追加全局索引、重复知识与断链审查。

## 六、反模式

- 把 API 字段表、通用 React 规范或一次性 PR 摘要写成 BUSINESS.md。
- 在根索引重复完整业务规则。
- 为了看起来完整而创建没有规则的空文档。
- 把推测当成已确认规则，或只引用 mock 而没有说明正式契约状态。
- 迁移后保留两份同等权威的文档。
